2. Diagram Type Decisions

2.1 Why SysML (not UML or BPMN)?

SysML (Systems Modelling Language) was selected over UML and BPMN for the following reasons:

  • Defence context: SysML is the standard modelling language for defence systems engineering (used in MBSE, DODAF, NAF frameworks). It is the natural choice for a defence-facing radar systems document.
  • Physical systems: SysML is designed for physical and cyber-physical systems (hardware + software + signal flow), not just software. Marine radar is precisely this kind of system.
  • Two diagram types used: Activity Diagram (behaviour / signal flow) and Block Definition Diagram (structure / components) together provide a complete MBSE view.
  • BPMN rejected: BPMN is optimised for business process flow; it has no concept of signal values, measurement accuracy, physical components, or system blocks.

2.2 Why an Activity Diagram + BDD (not just one diagram)?

DiagramWhat it showsWhy needed
Activity Diagram Temporal signal flow: what happens, in what order, with what decisions Captures the radar ingestion pipeline as a process — the "how it works over time" view
Block Definition Diagram System structure: what blocks exist, their properties, and how they relate Captures the system composition — the "what it is made of" view. Required for any MBSE-compliant model.

3. Format & Tooling Decisions

3.1 Format evaluation

Format Offline? Editable? No install? Decision
PlantUML (.puml) Partial — needs local JAR or web server Yes (text) No (Java + JAR) Rejected — web dependency for rendering; user explicitly excluded
Mermaid Partial — CDN or local bundle Yes (text) No Rejected — user explicitly excluded
Draw.io XML (.drawio) Yes (desktop app) Yes No (needs draw.io app) Not selected — requires installing draw.io Desktop
SVG (static hand-written) Yes (any browser) Hard — raw XML Yes Not selected — poor modifiability for non-developers
Local Web App (HTML/CSS/JS) Yes — Python http.server Yes — edit JS data objects Yes (Python built-in) Selected — fully offline, easily modified, no installs beyond Python

3.2 Why a local web app over a single HTML file?

  • Separation of concerns: Diagram data (the content) lives in js/activity.js and js/bdd.js as plain JavaScript objects at the top of each file. Non-developers can modify labels, add steps, and change lane names without touching rendering code.
  • Maintainability: Separate CSS, JS, and HTML files are easier to version-control and diff than a monolithic single HTML file.
  • No CDN calls: All assets are local. Zero network requests. Safe for air-gapped environments.
  • Python http.server: Python 3 is pre-installed on the machine. python3 -m http.server 8080 requires no additional installation and is a single command.

3.3 How to modify the diagrams

Open js/activity.js and edit the ROWS array at the top:

  • To add a step: add a new object to ROWS with type: 'process'
  • To rename a step: change the label field (use \n for line breaks)
  • To add a parallel branch: add multiple nodes in one row's items[]
  • To add a decision: use type: 'decision'
  • To change lane colours: edit the LANES array at the top

For the BDD, open js/bdd.js and edit BLOCKS and CONNECTIONS.

4. Hybrid Navy Flow — Design Decisions

4.1 What is the Hybrid Navy flow?

The Hybrid Navy flow represents a modern naval integration layer that runs in parallel with the standard radar pipeline. It does not replace radar — it augments it by fusing multiple sensor streams into a unified operational picture. This reflects current and near-future maritime defence architecture where standalone radar is insufficient for modern threat environments.

4.2 Why parallel (not sequential)?

The Hybrid Navy layer is modelled as a parallel fork from the Display & Plotting lane, not as a downstream sequential stage. Rationale:

  • AIS, satellite, and ECDIS feeds ingest continuously and independently of radar scan cycles
  • Sensor fusion must correlate tracks in real time — it cannot wait for the radar pipeline to complete
  • In SysML, concurrent activities that share a common trigger are correctly represented as fork/join pairs
  • The parallel model also correctly represents the degraded-mode scenario: if radar fails, the Hybrid Navy layer continues to operate from AIS and satellite feeds

4.3 Component selection rationale

ComponentRationale for inclusion
AIS Receiver AIS provides vessel identity (MMSI, name, flag) that radar echo cannot. Combined radar+AIS track is the foundation of modern ARPA. Gap detection (vessel with AIS off) is a key threat indicator.
Satellite Data Feed (VDES/GNSS) VDES (VHF Data Exchange System — IMO successor to AIS) provides beyond-horizon vessel data. GNSS augmentation improves own-ship position accuracy which directly improves relative target position.
ECDIS Overlay Electronic Navigational Chart integration allows fused tracks to be displayed in chart context — essential for navigational decision-making and COLREGS compliance assessment.
Drone / UAV Sensor Feed UAVs extend the sensor horizon beyond radar range, particularly relevant for littoral operations. Unmanned surface/air vehicles are now standard in hybrid naval doctrine.
AI / ML Target Classifier Classifies targets by vessel type, detects anomalous movement patterns (loitering, AIS spoofing), and assigns threat scores — capabilities beyond traditional ARPA.
Sensor Fusion Engine The core integration component. Correlates radar tracks with AIS, satellite, and UAV data to produce a single authoritative track per target — eliminates duplicate tracks and gaps.
Integrated Bridge System (IBS) The unified display and control system. Required by IMO MSC.252(83) for ships fitted with IBS. Presents the fused operational picture to the Officer of the Watch.

6. Swim Lane Structure — Design Decisions

The five swim lanes were derived directly from the four major hardware components described in the source (§4: Transmitter, Scanner, Receiver, Display) with a fifth lane added for the Hybrid Navy parallel flow.

  • Lane = responsibility boundary: Each lane maps to a distinct physical subsystem with clear input/output interfaces. This matches the SysML principle that swim lanes represent partitions of responsibility.
  • Lane ordering = signal flow: Lanes are ordered top-to-bottom in the sequence the radar signal traverses them — from transmission through to display. This makes the pipeline immediately readable.
  • Hybrid Navy as a separate lane: The Hybrid Navy flow is given its own lane because it represents a distinct system that interfaces with (but is not part of) the core radar hardware. Placing it in the Display lane would incorrectly imply it is a component of the display subsystem.
